- Why it missed them: InstalledApps read this Mac's five applications folders alone. A Finder alias is no symbolic link but a bookmark file, which `Bundle(url:)` reads nothing from, so an alias named anything was dropped; a link not named `.app` was never followed either.
- The volumes read (`InstalledApps.volumes`, from the kernel's mount table with MNT_NOWAIT and the I/O Registry's APFS roles, nothing on a volume read): mounted directly in /Volumes, no dot name, local, writable, shown in Finder, no APFS role. Their Applications folder (`applicationFolders(on:)`) when it is a folder, not a link, and the volume holds no macOS (`System/Library/CoreServices/SystemVersion.plist`). So never a network share, a disk image of an installer (read-only, and its Applications a link to /Applications), a disc, Recovery (this Mac has it at /Volumes/Recovery, writable but nobrowse, role Recovery), macOS's own volumes, another Mac's system or data volume (a bootable clone), or a Time Machine backup. A writable disk image someone mounted, with an Applications folder at its top, is read like a drive. Of one app in several places, this Mac's copy wins, then the volume first by name (but a link or an alias in this Mac's folders is found with them: the copy it points at wins).
- Links and aliases (`app(at:reach:)`): still never walked into, at any depth; one that points at an app lists that app at its own path (links resolved). Where it points is read from it first (a link's text, an alias's bookmark path), so one that points where the look does not go is never looked up there; an alias is resolved with `.withoutUI` and `.withoutMounting`. A link or an alias to a folder is not followed (a link to a drive's root would walk the whole drive), nor one onto a share.
- Two looks (WindowCatalog), one after the other on a serial queue of their own: the first, at start, reads this Mac's own disk alone (of the home folder, ~/Applications alone: the review's), as before, so its list goes out as fast as before; the second the volumes too, and whatever links and aliases point at on them or in the rest of the home folder, when a device connects (the review's: `secondLookDue`). Why: reading a removable volume can make macOS ask "Sill would like to access files on a removable volume", and the read waits for the answer, for as long as nobody is at the Mac (a person away, on Remote Access); a slow or sleeping disk waits too, and so does a read in Downloads, Desktop, Documents or iCloud Drive (a question of its own, or a file coming down from the cloud). A folder given that leads into /Volumes (~/Applications on a drive), or into the home folder past ~/Applications, waits for the second look. The queue is not the cooperative pool, which a wait that long would hold a thread of.
- Again as volumes come and go, while a device is connected: under the AppKit loop (Sill.app) NSWorkspace's mount, unmount and rename notifications bring a look 2 s after the last of a burst, only when the volumes of one's own changed, so a disk image, a share, Time Machine's hourly mounts or Recovery bring none and wake no disk. With no device connected nothing is read: the next device's arrival compares the volumes with the last look's and looks when they changed, also in the CLI, which hears no notification (dispatchMain delivers none; `--virtual-display` runs the AppKit loop). The list goes out again when it changed (the first look's always, as before). Sill.app starts at login, which can come before an external drive is mounted: without this its apps would show only after the next start. Spinning disks: read when a device connects after they changed and at those changes, never for a device's list.
