**The Apps list shows the apps on the Mac's other disks, and the apps Finder aliases point at (2026-11-18, branch `external-drive-apps` from main at eb48ac9).** Issue #370 (tsvoronos, macOS 27.2.1, Sill 0.6.0, Remote Access): apps the App Store put on an external drive (its "Download and install large apps to a separate disk") never showed in the Apps list, nor did aliases to them in /Applications. Noah answered "Will look into this thanks for reporting!" on 11-16. Host only: no wire change (the list already travels as kind 5, and a device replaces its list with each one), no iOS change.
- Why it missed them: InstalledApps read this Mac's five applications folders alone. A Finder alias is no symbolic link but a bookmark file, which `Bundle(url:)` reads nothing from, so an alias named anything was dropped; a link not named `.app` was never followed either.
- The volumes read (`InstalledApps.volumes`, from the kernel's mount table with MNT_NOWAIT and the I/O Registry's APFS roles, nothing on a volume read): mounted directly in /Volumes, no dot name, local, writable, shown in Finder, no APFS role. Their Applications folder (`applicationFolders(on:)`) when it is a folder, not a link, and the volume holds no macOS (`System/Library/CoreServices/SystemVersion.plist`). So never a network share, a disk image of an installer (read-only, and its Applications a link to /Applications), a disc, Recovery (this Mac has it at /Volumes/Recovery, writable but nobrowse, role Recovery), macOS's own volumes, another Mac's system or data volume (a bootable clone), or a Time Machine backup. A writable disk image someone mounted, with an Applications folder at its top, is read like a drive. Of one app in several places, this Mac's copy wins, then the volume first by name.
- Links and aliases (`app(at:reach:)`): still never walked into, at any depth; one that points at an app lists that app at its own path (links resolved). Where it points is read from it first (a link's text, an alias's bookmark path), so one that points where the look does not go is never looked up there; an alias is resolved with `.withoutUI` and `.withoutMounting`. A link or an alias to a folder is not followed (a link to a drive's root would walk the whole drive), nor one onto a share.
- Two looks (WindowCatalog), one after the other on a serial queue of their own: the first reads this Mac's own disk alone, as before, so its list goes out as fast as before; the second the volumes too, and whatever links and aliases point at on them. Why: reading a removable volume can make macOS ask "Sill would like to access files on a removable volume", and the read waits for the answer, for as long as nobody is at the Mac (a person away, on Remote Access); a slow or sleeping disk waits too. A folder given that leads into /Volumes (~/Applications on a drive) waits for the second look. The queue is not the cooperative pool, which a wait that long would hold a thread of.
- Again as volumes come and go: under the AppKit loop (Sill.app) NSWorkspace's mount, unmount and rename notifications bring a look 2 s after the last of a burst, only when the volumes of one's own changed, so a disk image, a share, Time Machine's hourly mounts or Recovery bring none and wake no disk. The list goes out again when it changed (the first look's always, as before). Sill.app starts at login, often before an external drive mounts: without this its apps would show only after the next start. The CLI under dispatchMain reads the volumes at start only. Spinning disks: read at start and at those changes, never for a device's list.
- A test host (`--synthetic`) reads no other volume and watches none: macOS would ask the app running it (Terminal, an agent's) whether it may read a removable volume (BUILD-AND-RUN.md, beside SILL_TEST_NO_SCREEN).
- The launch: Launch Services' copy by bundle ID first, as always, then the path the list found (`installedAppURL`), for an app on another disk Launch Services never registered. Nothing from the pick to the stream assumes /Applications (the pending launch picks the first window of that bundle ID).
- Info.plist: NSRemovableVolumesUsageDescription, "Sill lists the apps on your external drives in the Apps list on your iPhone and iPad.", the words macOS's question shows.
- Logs: the first look's line is the same text as before; the second prints only with a volume of one's own or after a change, naming the volumes and how many apps each Applications folder gave ("installed apps with /Volumes/Drive: 91 in 37 ms (+ icons 18 ms); listed from /Volumes/Drive/Applications: 4"). A count of 0 for a folder with apps in it means macOS refused Sill (Don't Allow).
- No switch: a bug fix that makes the list show what the Mac has installed, as Launchpad and Spotlight do; macOS's own Files & Folders › Removable Volumes is the switch for reading a removable drive, and a switch of Sill's would need Settings, a key and, to reach a device's Settings panel, the wire. Noah's call (the PR says so).
- Checked: `Tests/checks/installed-apps` gains a fake /Volumes and a made-up mount table (fifteen volumes, one of each kind above), Finder aliases made as Finder makes them (bookmark files) and links in and out of it, an alias whose app moved off the drive and a link through a link (both tell that where it points is read before resolving), and one line that reads the real mount table; 19 mutants more, 31 in all. On this Mac's own folders, main's InstalledApps against this one: the same 123 apps, names and order; two paths differ, the links resolved (Safari's cryptex, Feedback Assistant in CoreServices). The real mount table here gives no volume of one's own.
