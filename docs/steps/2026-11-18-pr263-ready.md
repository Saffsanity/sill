- What the review found, and what became of each:
  - **Not measured: whether these commands ever fire on a Mac.** #263's premise is that the Mac's menu
    bar takes ⌘W, ⌘C, ⌘V and the rest before `pressesBegan`. On an iPad the menu bar's probe measured the
    opposite (docs/menu-bar-plan.md, "Why the device never registers the Mac's shortcuts as key
    commands": while InputOverlay is first responder, ⌘C/V/Z/A/,/W all reached its `pressesBegan`, with
    or without `wantsPriorityOverSystemBehavior`), and UIKit's header says that property is about the
    focus and text-editing systems, not menus. jmstacey's report may have been made with nothing first
    responder (before #80 no keyboard was held without the Keyboard button, and on a Mac GameController
    may report none before the first key), and with nothing first responder the menu bar's ⌘W closes
    Sill's window on an iPad too. But on a Mac AppKit offers a ⌘ key equivalent to the window and the
    menu bar before it is an ordinary key down, so the premise may hold there. Three outcomes, none
    measured: every shortcut reaches `pressesBegan` once the view holds the keyboard (the first part
    alone fixes #129's keys, the commands never fire); the commands win (the second part is what fixes
    them); or the menu bar wins over both (neither part fixes ⌘W: the fix would be Sill's own File ›
    Close and the like out of the menu while a session holds the keyboard). Added: DEBUG
    `-SillMacKeyCommands 0|1` (the commands off or on for a run, on by default only on a Mac), a console
    line saying which, and the command's character in its `hwkey:` line (`hwkey: usage 26 down via
    keyCommand "w" (command): to the Mac`), so one Debug run on a Mac with and without them answers it.
  - **The wrong shortcut on other layouts, where the commands do fire.** A key command names a
    character, and its action is told nothing of the key pressed (UIKeyCommand.h: one `sender`). The
    command's character goes as the key a US keyboard types it with, while every other key goes as the
    key pressed (`pressesBegan`'s usage, which the streamed Mac reads with its own layout, as a keyboard
    plugged into it). With AZERTY on both Macs: ⌘A (the key at US Q) arrives as usage 0x04, the streamed
    Mac's Q, so ⌘Q quits its app; ⌘Z arrives as ⌘W and closes its window; ⌘W as ⌘Z; ⌘M as ⌘, (its
    Settings). QWERTZ on both: ⌘Z as ⌘Y. A US layout on both is right. Not fixable inside the command
    without the key; written down in `shortcutCommandKeys`' comment, docs/DEVELOPMENT.md and here, and
    left for Noah to decide with the Mac's answer (it holds the merge where the commands fire). The ways
    out then: keep only the commands for what the menu bar would take (the third test lists them); claim
    a character only once this keyboard has been seen typing it, and send that key; or take Sill's own
    menu items out while the stream holds the keyboard, so every key reaches `pressesBegan` as pressed.
