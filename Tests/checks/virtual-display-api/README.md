# `virtual-display-api`

**Checks:** the virtual display's private API surface and how the runtime's type encodings are matched against it (#87, #62), decided by `Runtime.method` itself: every method's encoding as the runtime reported it on an M2 Pro with macOS 27.0.1, natively and under Rosetta, passes for its entry, and so do `applySettings:`'s "c@:@", printed on an Intel Mac mini with macOS 15.7.3 (#87), and its "B@:@", inferred, not printed, from an x86_64 build that took "B" alone passing the self test on an OpenCore machine with macOS 26.7.1 (#62); one entry per measured method, written without offsets; a `BOOL` return passes spelled "B" or "c" and nothing else does (another type, an argument, a void return; written "c", it stays "c"); the offsets come off and nothing else; `applySettings:` sent as `init` sends it to a method typed `B24@0:8@16` or `c24@0:8@16` reads its YES and its NO, and one typed `C24@0:8@16` is refused with `checkPrivateAPI`'s line. On arm64, CI's architecture, the only "c" methods it runs are its own classes': a `CGVirtualDisplay` reports "c" only under Rosetta or on an Intel machine. And on arm64 `ObjCBool` compiles to the same code as `Bool`, so its x86_64 reading (any byte but 0 is YES) is not checked in CI; `HeadlessDesktopPolicy` (#61, #298: when Sill's fallback Desktop display is made and kept, the display pool, and the built-in screen's size)

**Compiles:** `Sources/SillHost/VirtualDisplay.swift` whole, as `VirtualDisplayProbe` compiles it (`build.sh`); its static surface and pure `TypeEncoding` run, and `Runtime.method`'s decision and the `applySettings:` call run (through `methodProblem` and `applySettings(_:to:)`, which `checkPrivateAPI` and `init` use) against classes the check makes at run time, so no private class is looked up and no display is made
